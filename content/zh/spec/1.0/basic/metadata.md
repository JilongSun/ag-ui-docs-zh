协议中几乎一切都携带一个可选（OPTIONAL）的 `metadata` 对象——事件（event）、消息（message）、工具调用（tool call）、工具、中断（interrupt）、恢复（resume）条目。它是承载协议未建模内容的开放通道：提供方名称、延迟、结束原因、token 计数、追踪键，以及应用想让数据顺带携带的任何东西。

## 取值

`metadata` 按键开放。键下允许任意 JSON 值，包括 `null`——那里的 `null` 是有意义的数据。该对象本身要么缺席，要么是一个对象，不得（MUST NOT）为 `null`。

未知的元数据（metadata）键在协议上是合法的，不属于未被识别的素材：[处理模型](processing.md)在任何键上都不会剥离它们。

## 键

`ag-ui` 键保留给协议自用。其他每个键都是应用空间；生产者（producer）应当（SHOULD）给自己发明的键加上厂商或应用名前缀，这样两个扩展同一条流的参与方不会撞车。

## 合并

流式产生的条目由若干事件拼装而成，而有意思的取值——token 用量、结束原因——只有在末尾才可知。因此元数据是累积的，而不是在条目打开时就固定下来：消费者（consumer）必须（MUST）把构成某个条目的每个事件的元数据逐键合并，每个键以后写者胜出。

合并不得（MUST NOT）递归。键的取值是整体替换的，因此键下的对象或数组会被整体替换，而不是与先前的值混合。

## 每个事件（event）的元数据（metadata）落在何处

合并需要一个目标，而目标就是该事件所构建的东西——并非总是那条消息：

| 事件 | 合并进 |
| --- | --- |
| `TEXT_MESSAGE_START` / `CONTENT` / `END` | 文本消息 |
| `REASONING_MESSAGE_START` / `CONTENT` / `END` | 推理消息 |
| `TOOL_CALL_START` / `ARGS` / `END` | **工具调用本身**——而不是拥有它的那条助手消息 |
| `TOOL_CALL_RESULT` | 它创建的工具消息 |
| `ACTIVITY_SNAPSHOT` / `ACTIVITY_DELTA` | 活动消息——累积的元数据能在替换性快照（snapshot）中存活（[活动（activity）](../events/activity.md)） |
| chunk（`*_CHUNK`） | 其合成事件所合并进去的对象（[chunk 元数据](patterns/streaming.md#分块元数据 metadata)） |
| 其他一切（`RUN_*`、`STEP_*`、快照、`RAW`、`CUSTOM`、……） | 无处可落——见下文 |

> [!NOTE]
> 工具调用的元数据落在调用本身而不是其父消息上，是刻意为之。一条助手消息可以拥有多次工具调用，若把它们的元数据折进父级，结果就会取决于这些调用恰好交错出现的顺序。每次调用各自保留自己的元数据，正是让它保持无歧义的原因。

不构建任何持久条目的事件没有合并目标：它的元数据属于该事件自己，对中间件（middleware）以及任何观察该流的一方可见，协议不会把它再分配到别处。消费者可以（MAY）把它呈现出来——比如把某次运行（run）的 `RUN_FINISHED` 元数据记进自己的记账里——但没有任何规则要求这样做。

## 存储的元数据（metadata）

消息、工具调用、工具、中断与恢复条目把 `metadata` 作为自身的一个普通存储字段携带。除了上文列出的那些事件，没有任何东西合并进这些字段；[运行输入（run input）](run-input.md)中某个工具的元数据，或某个中断的元数据，只是随其载体旅行的数据。

## 数据类型

[`Metadata`](../schema.md#metadata) 由 [schema 参考](../schema.md)定义，其中每个载体的条目都会列出它的 `metadata` 字段。
