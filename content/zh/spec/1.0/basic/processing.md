有两样东西表面上相似，却绝不能被混淆：协议未描述的素材，以及协议确实描述了某个东西、但取值是错的。前者是协议生长的方式。后者是一个 bug。

## 规则

**未被识别的素材不是错误。畸形的已知取值才是。**

- 类型为本实现所不识别的事件（event）不得（MUST NOT）中止运行（run）。
- 某事件上未描述的属性不得（MUST NOT）中止运行。
- 实现不认识的联合成员——一种新类型的内容片段、在其发布之后才命名的一个结果——不得（MUST NOT）中止运行。
- 协议*确实*描述的字段若携带 schema 拒绝的取值，必须（MUST）是致命的：消费者（consumer）必须（MUST）让运行失败，而不是修复、强制转换或忽略该取值。

这种不对称是刻意的。某个事件类型在实现发布之后才加入，这是可以预期的——发送方更新，旧的一方没有依据说它无效。但 `messageId` 里装着一个数字并不是更新的协议；那是一个缺陷，悄悄把它强制转换掉的消费者会把该缺陷藏起来，直到它以更难诊断的形式浮现。

## 每种传输（transport）给出相同的答案

这些规则约束的是协议，而不是某种线上格式。支持不止一种传输（transport）的消费者必须（MUST）对同一个事件作出相同的判定，无论它是怎么到达的：一条流若作为 JSON 能存活，作为 protobuf 也必须（MUST）能存活；若失败，也必须（MUST）以同样的方式失败——除非二进制编码本身无法表达判定所依赖的那点差异，也就是本页下文提到的两种情形（无法命名的信封变体，以及 protobuf 会实体化出来的那些缺席）。

这就为读取器能自行决定的事情划定了界限。把字节变成事件是读取器的全部职责——某个帧的字节完全映射不到任何事件就是解码失败，这个判断确实属于读取器。而一个成功读出的事件是否携带实现认得的东西，则不属于它：那个问题属于每种传输共享的那一个阶段。同时也做校验的读取器会让自己的传输比其他传输严格得多，于是生产者（producer）对内容类型的选择就决定了某次运行能否存活。

二进制情形需要一处迁就。文本读取器可以把一个未知类型的事件传递下去，因为类型是以字符串传输的，共享阶段可以按名称丢弃它。二进制读取器做不到：一个它未曾针对编译过的信封变体不携带任何可以传递下去的名称。这样的帧必须（MUST）被丢弃，并给出告警，而不是让运行失败——这正是共享阶段本该给出的答案，只是改用了一种无法推迟该问题的传输的措辞。

> [!NOTE]
> 只要二进制编码给某个字段不留存在性，它就无法兑现这一点。在 protobuf 中，这同时涵盖必需（required）的标量与必需的数组：生产者省略的必需字符串会以空字符串到达，必需数组会以空数组到达，而二者都会被接受，同一事件以 JSON 形式出现时却会被当作畸形拒绝。schema 本就禁止省略它们，所以这改变的是一个有缺陷的生产者如何被诊断，而不是一个符合一致性（conformance）的生产者可以发送什么。

## 消费者（consumer）如何处理未被识别的素材

向应用代码暴露事件的消费者不得（MUST NOT）把未被识别的素材当作协议描述过的内容投递出去。读入这类素材之后，这样的消费者必须（MUST）做以下之一：

- **丢弃它**，如果整个事件都是未被识别的类型。消费者应当（SHOULD）发出指明该类型的告警。
- **剥离它**，如果它是某个本来有效的事件上的未知属性或未被识别的联合成员。消费者应当（SHOULD）发出指明被移除路径的告警。

消费者不得（MUST NOT）让被剥离的属性残留在应用代码收到的值里，也不得（MUST NOT）让被丢弃的事件到达那里。

这只在 schema 封闭对象的地方适用，而凡是它描述协议自有对象之处，都是封闭的。在 schema 刻意让对象保持开放的地方，它未描述的成员根本不是未被识别的素材，必须（MUST）保留。JSON Patch 操作就是这种情形：RFC 6902 第 4 节要求操作忽略它未定义的成员，而不是拒绝它们，因此一个多带了 `value` 的 `remove` 仍是合法的补丁，并会完整到达。在那里做剥离的消费者删掉的是一致的数据，它发出的告警毫无所指。

这条约束的是管道，不是解析器。只解析事件的库层——比如各 SDK 中生成的模型——会刻意保留未知属性，好让它上方的中间件（middleware）仍能看到它们。提供这种解析器却没有执行阶段的 SDK 尚未满足这条规则；目前是 Python 与 .NET，它们的模型以宽容方式解析，没有任何在应用代码之前执行剥离的阶段。

> [!NOTE]
> 有一种情形参考实现尚未满足：schema 为封闭字符串取值集合的字段——例如消息（message）的 `role`——是作为叶节点检查的，因此那里未被识别的取值是致命的，而不是被剥离。.NET 的转换器也以同样方式拒绝未知的角色或结果。上面的规则才是协议的要求；这两者都是相对该规则的缺口，而不是对它的一种软化。

剥离会一路向下，它移除什么取决于无法识别的取值位于何处：

- 位于**可选（optional）**位置时，该字段被移除，它周围的一切都保留下来。
- 位于**必需**位置时，改为移除*包含*它的那个值。若某个媒体片段的来源是本实现从未听说过的类型，该片段会被整体移除——留下一个没有来源的片段会给校验器交出它必须视为畸形的东西，把一个新增变成致命错误。
- 位于**列表**内部时，无法识别的元素被丢弃，列表本身保留。

## 中间件（middleware）处于何处

中间件——消费者为翻译、观察或改写流而安装的任何东西——必须（MUST）在执行之前运行，而执行必须（MUST）在校验之前、在应用代码看到任何内容之前运行。

```
producer → compatibility boundary → middleware → enforcement
         → chunk expansion → verification → application
```

兼容边界是针对协议已退役形状的常开翻译器。它必须（MUST）最先看到流，因为已退役形状可能就是一个 chunk，而更早遇到它的阶段要么会在它上面失败，要么会把它变成该边界再也认不出的东西。中间件*链*可以（MAY）在自己的各阶段之间展开 chunk，好让每个阶段都收到 start/content/end 形式——参考实现的链式辅助工具正是这么做的。因此中间件必须（MUST）对两种形式都有准备：它看到什么取决于它在链中的位置。

阶段之间的展开会收窄一项保证，而这种收窄是明说的，不是隐藏的：展开合成的事件只携带协议定义的内容，因此 *chunk 上*未被识别的字段只有在上述规范顺序下才能存活到执行——并挣得它的告警。过早展开的链会静默地丢失它们。符合一致性的生产者从不发出这类字段，所以丢失的是来自更新协议版本、穿越了一条过早展开的链的素材。展开本应负责投递的素材——增量（delta）、开启字段、元数据（metadata）、`rawEvent`、归属——都完好无损地传递过去；chunk 的 `timestamp` 则不然，因为合成出来的事件并不是那个 chunk，而且与未知字段一样，只有在规范顺序下，它才会在展开之前被判定。

chunk 本身就是一个事件，必须（MUST）被当作一个事件来判定：无论哪个阶段先遇到畸形的 chunk——在上述规范顺序下是执行，在中间件链提前展开之处是展开——都必须（MUST）拒绝它而不是修复它，并且不得（MUST NOT）归一化、填默认值或掩盖一个执行会拒绝的畸形已知取值。用默认值替换畸形角色的消费者，让同一个生产者缺陷在明文发送时是致命的、以 chunk 形式发送时却不可见，于是生产者恰好用了哪种形式，决定了它的 bug 是否曾被报告。

校验必须（MUST）在展开之后运行，因为它检查的东西——消息与调用先开启、再继续、最后关闭——只有在 chunk 变成它所代表的事件之后才存在。

这个顺序在两个方向上都是承重的：

- 中间件必须（MUST）在执行移除素材之前看到它。兼容垫片存在的意义正是翻译当前协议未描述的某种形状；如果执行先剥离了那种形状，垫片收到的就是一个无可翻译的事件，而这次运行会丢失无人能恢复的数据。
- 应用代码不得（MUST NOT）看到执行会移除的素材。一旦各翻译器都有过机会，仍然未被识别的东西就是未被识别的，到此为止。

消费者必须（MUST）在每一条为应用代码产生事件的路径上应用这一顺序，包括重连与重放。跳过执行的路径是保证上的一个洞，而不是一种优化。

## 出站素材

同一套边界也适用于消费者发送的内容。在传输之前，消费者必须（MUST）从运行输入（run input）中移除未被识别的素材，应当（SHOULD）就自己移除了什么发出告警，并且必须（MUST）在任何内容发出之前把畸形的已知字段视为致命。

接收运行输入的生产者必须（MUST）对它应用同样的不对称性：未被识别的素材不会让输入无效，畸形的已知字段则会。

## 生产者（producer）不得做什么

生产者不得（MUST NOT）抱着消费者会忽略它的期望，发出协议未描述的事件类型。未被识别的事件得以存活，是为了让协议能新增它们，而不是为了让生产者借流夹带私有信令；`CUSTOM` 与 `RAW` 正是为此而存在，并且由 schema 描述。
